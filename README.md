# Noida Research Agent

A prototype tool-using research agent that investigates a Noida location (query, sector, or
city based) by orchestrating News, Weather, and Traffic tools, then synthesizes the results
into a short, source-cited report.

## Architecture

```
app/
  config.py            Settings loaded from .env (fails fast if GROQ_API_KEY is missing)
  schemas.py            Pydantic contracts: request/intent/plan/tool I/O/report state
  harness/              Execution & reliability layer (separate from agent reasoning & tools)
    registry.py          Tool registry: name, purpose, input/output schema, timeout, retries
    executor.py           Validates input, enforces timeout + bounded retries, never raises -
                           failures become NormalizedResult(status="failed") so the pipeline
                           continues with partial results
    logging_setup.py      Structured JSON logs (run_id, stage, status, duration), secret-redacted
    errors.py              TransientToolError (retryable) vs ToolInputError (not retried)
  tools/                 News / Weather / Traffic tools + shared geocoding
  agent/
    graph.py              LangGraph pipeline: parse_intent -> plan -> orchestrate -> synthesize -> report
    prompts.py             System prompts (intent parsing, planning, evidence-aware synthesis)
    report.py              Deterministic Markdown templating from verified tool/synthesis data
                           (final report text is assembled in code, not freely generated by
                           the LLM, so citations/timestamps can't be hallucinated)
  main.py                FastAPI app: POST /research, GET /health, serves static/index.html
static/index.html        Minimal frontend (mode selector, report view, bonus 2D map)
```

### Orchestration pipeline (LangGraph)

1. **parse_intent** - Groq LLM extracts city/sector/topic/time-sensitivity/constraints from the
   user's mode + input (structured output).
2. **plan** - Groq LLM proposes research questions and which tools to call (all three for a
   broad overview).
3. **orchestrate** - the harness resolves the location (geocoding, with a disclosed city-level
   fallback when sector-level data isn't available) and runs the planned tools **in parallel**
   with per-tool timeouts/retries.
4. **synthesize** - Groq LLM combines the normalized evidence into an executive summary, area
   insights, conclusion, and caveats. Retrieved tool content is explicitly treated as untrusted
   data; the prompt instructs the model to ignore any instructions embedded in it and to avoid
   unsupported claims.
5. **report** - the final Markdown report is assembled deterministically in code from the
   synthesis text plus the verified tool facts, sources, and timestamps.

A `run_id` (UUID) is generated per request and attached to every structured log line, so a
single research request's stages can be traced end-to-end.

## Tools and data sources

| Tool | Live source | Fallback when unconfigured |
|---|---|---|
| News | [NewsAPI.org](https://newsapi.org) (`NEWS_API_KEY`) | Clearly-labelled mock article, flagged `is_mock: true` |
| Weather | [Open-Meteo](https://open-meteo.com) (no key needed) or OpenWeatherMap if `OPENWEATHER_API_KEY` is set | n/a - Open-Meteo is live by default |
| Traffic | [TomTom Traffic API](https://developer.tomtom.com) (`TOMTOM_API_KEY`) | Clearly-labelled mock congestion + general Noida connectivity context, flagged `is_mock: true` |

Sector-level geocoding (e.g. "Sector 150") is not available in public gazetteers, so the app
falls back to the Noida city center and **discloses this in the report's limitations** rather
than fabricating sector-precise coordinates.

## Setup

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
copy .env.example .env          # then edit .env and set GROQ_API_KEY
```

Get a free Groq API key at https://console.groq.com/keys. News/Weather/Traffic API keys are
optional - the app runs with clearly-labelled mock data for any of them that are unset.

## Run

```bash
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Open http://127.0.0.1:8000 - pick a mode (query / sector / city), enter input (e.g. `Noida`,
`Sector 62, Noida`, or `Assess infrastructure and connectivity around Noida Sector 150`), and
click **Run research**.

The same pipeline is reachable directly via API:

```bash
curl -X POST http://127.0.0.1:8000/research \
  -H "Content-Type: application/json" \
  -d "{\"mode\": \"city\", \"input_text\": \"Noida\"}"
```

## Bonus: map view

The frontend shows a 2D OpenStreetMap view (Leaflet, no key required) centered on the resolved
location as a demo visualization. A true 3D building view would require a Mapbox token, which
is not configured in this prototype - the UI discloses this limitation rather than faking it.

## Known limitations

- Sector-level weather/traffic use city-level coordinates (disclosed in the report) since Noida
  sectors aren't in public geocoders.
- Without `NEWS_API_KEY` / `TOMTOM_API_KEY`, those tools return labelled demo data, not live data.
- The harness retries transient failures (timeouts, 5xx) up to 2 times per tool with backoff; a
  tool that still fails is marked failed and excluded from the report rather than blocking it.
